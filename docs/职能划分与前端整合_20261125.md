# 车群算力池：资源池与任务编排的职能划分及前端整合（2026-11-25）

## 1 对原有理解的辨析

| 原有理解 | 判断 | 依据与调整 |
|---|---|---|
| 平台最终是面向长安其他业务的通用算力平台：用户按约定提供模型环境与启动器，或交付符合接口的容器，由本平台调度执行 | 方向成立，按现有契约推进 | 与 11.13 通用任务接入设计、11.18“两模板 + 预留契约”的约定一致。中期只上视频分析、航拍建图两个模板，不开放任意镜像。本次把“模板”作为任务创建、触发策略、统计三处的一级维度，后续接通用模板时只需增加一种模板，页面结构不再改变 |
| 最初设想由顾强强创建任务、筛选节点，方雍执行调度 | 现已不适用，结论正确 | 任务的创建、调度与执行状态都在任务库中，归属调度侧，避免同一任务出现两个创建入口和两套状态。资源池负责“节点能否参与”，不负责“任务做什么” |
| 任务创建需对接节点管理，支持自动或手动选点后再执行 | 成立，但需要补一个前提 | 选点不应在资源池页面上一次性完成后“交给”调度器。执行前资源会变化，所以采用两段式：资源池给出第一阶段准入，即审批、入池、管理员暂停、集群/标签/硬容量；调度侧再核对运行可行性，即健康、快照时效、执行槽、内存、模型/架构，然后选点。每个工作单元在下发时都会重新核对，手动指定只是一个硬范围，不能绕过准入 |
| 候选节点筛选、失联核对、工作流与能力、触发策略、历史与对比等页面意义不明确，可清理 | 部分成立 | 这几页对应甲方 11.21 验收表第 15、25、34、35、37、38 项，背后的能力不能删，只是入口放错了位置。处理方式是合并到所属页面。真正没有必要的只有三项：独立的候选筛选页、执行侧节点卡片页，以及已被 11.21 表移出中期验收的 API 连接器、认证插件和五类能力验证入口 |

## 2 职能划分（今后开发的边界）

| | 资源池（顾强强） | 任务编排与执行（方雍） |
|---|---|---|
| 回答的问题 | 哪些节点存在、可信、在池、可被调度；资源池总量多少 | 做什么任务、在哪些节点上做、怎样下发、重试和恢复 |
| 数据所有权 | `data/pool.db`：物理身份、审批、入池、调度开关、集群、标签、Agent 采样 | 任务库：任务、工作单元、尝试、会话、调度决策、告警、失联记录、策略、算法参数 |
| 页面 | 资源池总览、节点管理（含暂停调度和执行投影）、算力池、集群管理、资源需求查询 | 运行总览、任务中心、调度策略、告警与恢复 |
| 对接接口 | 第一阶段准入由 `PoolBridge.annotate` 与 `requirement_reasons` 提供，在 enforce 模式下作为过滤条件；节点↔执行节点绑定见 `/api/v1/platform/bindings` | 统一选点预览为 `/api/scheduling/candidates`，两阶段的结论在同一张表；资源池页面读取 `/api/v1/scheduler/executions`、`/api/v1/platform/summary` 等任务库投影 |
| 节点开关 | **唯一的暂停或恢复入口**是节点管理中的“暂停调度” | 不再在任务侧放“停止新任务分配”按钮；后端接口暂时保留，用于兼容与故障注入测试 |
| 断网恢复（验收 25） | 节点重新接入、资源同步耗时 | 受影响任务记录、链路恢复后的状态核对、继续执行或有限重试 |
| 定时（验收 20 与 35） | K8s Job/CronJob 管理 | 业务触发策略（服务/周期）创建任务实例；二者不重复 |

## 3 页面整合结果

任务侧由 9 个栏目收敛为 4 个；资源池保留 5 个栏目，其中一个改名并调整作用。

| 原入口 | 处理 | 现位置 |
|---|---|---|
| 运行总览 | 保留，新增“调用统计”面板，按天 × 工作流统计调用次数、成功、失败、超时、取消、在途与成功率（验收 38） | 运行总览 |
| 任务中心 | 保留；新建任务弹窗内置“执行节点”区块（见第 4 节） | 任务中心 → 任务列表 |
| 历史与对比 | 按天统计移到运行总览；同条件运行对比作为子页签 | 任务中心 → 运行对比 |
| 候选节点筛选 | 删除独立页。候选与排除原因在新建任务时预览，执行后在任务详情的“调度决策”中逐尝试追溯（验收 15） | 新建任务 / 任务详情 |
| 触发策略 | 改为“调度策略 → 触发策略”。可以绑定视频分析或航拍建图模板，维护默认参数（JSON），支持新建、编辑、启停、删除、手动执行；列表显示绑定模板、默认算法、选点方式及最近一次触发（验收 35） | 调度策略 → 触发策略 |
| 工作流与能力 | 拆分：算法参数管理保留为“调度算法”，支持新建、编辑、删除、上传和导出（验收 34）；API 连接器、认证插件和五类能力验证的入口下线，后端接口保留，供中期后通用工作流使用 | 调度策略 → 调度算法 |
| 站内告警 | 保留 | 告警与恢复 → 任务告警 |
| 失联与任务核对 | 并入告警页（验收 25 的任务侧） | 告警与恢复 → 节点失联与任务核对 |
| 执行节点 | 删除。节点状态、暂停调度、执行投影统一放在资源池节点管理，避免两处开关 | 资源池 → 节点管理 |
| 资源筛选与提交（资源池） | 改名为“资源需求查询”，只做第一阶段容量与准入查询，包括集群聚合是否满足需求。删除“提交执行（示例视频）”、调度请求 JSON 和未配置的 Scheduler 占位；新增“以此范围新建任务”，把选中节点映射为执行节点后带入任务创建 | 资源池 → 资源需求查询 |

旧链接仍可打开：`?page=candidates/compare` 跳到任务中心，并进入对应子页签；`workflow/strategies` 跳到调度策略；`incidents` 跳到告警与恢复的失联页签；`nodes` 跳到资源池节点管理。

## 4 新建任务的选点流程

1. 选择模板，填写输入与参数。
2. 在“执行节点”区块选择 **自动选点**（默认，`node_ids=[]`，由调度算法在所有满足条件的节点中逐单元选择）或 **手动指定**（视频分析与单节点建图可勾选一个或多个节点；协同建图至少两个）。也可以设置资源池集群、能力标签，视频任务还可以设置 CPU 核数和 GPU 数量下限。
3. 表格实时调用 `/api/scheduling/candidates`，请求体与即将提交的任务一致。每个节点显示结论、排除原因（标明“资源池”或“执行侧”）和评分。自动模式下标出当前首选；节点名链接到资源池节点详情。
4. 手动选择了当前不满足条件的节点时，界面会如实提示：任务只会在条件恢复后使用这些节点，期间可能排队。
5. 也可以从资源池“资源需求查询”的第 3 步带入节点范围，地址为 `/pool/console?page=tasks&new=<模板>&nodes=<执行节点>`。

## 5 接口与代码变更

- `POST /api/scheduling/candidates`：`params` 可同时接受视频分析和航拍建图的任务体；建图请求按 `candidate_params` 补齐应用标识和 CPU 下限。返回值增加 `workflow_id`，`requirements` 为实际参与判定的参数。
- 触发策略：`params` 可以是 `MappingInput` 或 `TaskInput`；服务触发和周期触发都按模板创建实例，建图实例也写入 `trigger_type` 与 `strategy_id`；不能创建时返回 422。
- `GET /api/overview/statistics?days=1..90`：按北京时间自然日和工作流统计。成功率 = 成功 /（成功 + 失败 + 超时），取消和在途不计入分母。
- 前端：新增 `web/src/NodeScope.jsx`；`TaskConsole.jsx` 栏目重组；`MappingTask.jsx` 改用统一选点；删除 `CandidateView`。资源池删除 `submitPoolTask`、`buildSchedulerSubmission`、`submitToScheduler` 和 `SchedulerSubmission`。
- 测试：新增 `tests/test_console_consolidation.py`（3 项）和 `web/e2e/task-console.spec.js`（4 项）；`metrics.spec.js` 夹具补充统计接口。

## 6 仍需组内确认

- 资源需求查询中的显存、NPU、DLA 下限目前只作用于查询本身，任务体尚无对应字段，只能通过带入的节点范围间接生效。是否把这些字段加入任务准入，需要与顾强强对齐 `requirement_reasons`。
- 验收 36、37（调度任务监控、调度日志）的责任人仍待确认。当前由运行总览、任务详情事件回放和任务中心检索覆盖。
- 前端最终统一到 TS + AntD 的迁移放在中期之后。本次没有改动资源池各页的视觉风格。
