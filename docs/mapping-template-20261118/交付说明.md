# 建图样例任务二：平台化适配交付说明

日期：2026年11月18日。性质：本期实现与真实 Thor 验证记录，不是后续能力承诺。

## 1. 本次范围

按用户确认采用“两个模板样例任务 + 后续通用任务”的路径：

- **本期启用：视频分析、航拍建图**。新建任务使用同一个“任务类型”下拉菜单；任务中心、历史、资源池、调度、K3s 生命周期共用；各模板有自己的输入、参数、镜像和成果页面。
- **本期不启用通用任务**。接口拒绝 `workflow_id=generic`；不接受用户自选镜像、命令或脚本。第三种类型及其安全准入在中期后实施，契约草案见《通用任务扩展契约》。
- 不部署 WebODM 的 Django/前端/账户项目管理，不部署 NodeODX、ClusterODX 或另一套排队调度系统。直接在独立 ARM64 CPU 镜像中调用 ODX 3.8.6；保留实际算法所需 OpenSfM/OpenMVS/GDAL 等运行依赖。
- Mac 原生管理与 OCI 仓库、Thor K3s 执行、服务器唯一业务源码开发的分工未变。

## 2. 落地流程

```text
同一个新建任务入口
  ├─ 视频分析 → 上传/示例视频 → 切分/模型参数 → 视频镜像
  │                                      → 每任务/节点一个K3s会话 → 检测结果与预览
  └─ 航拍建图 → 照片ZIP → 标准/快速、分辨率、并行度 → 建图镜像
                                         → 单节点K3s Job → 文件清单校验 → 正射预览与下载
共同：输入标识 → 任务/工作单元/attempt → 资源池资格 → 资源约束选点 → 实际Pod身份
      → 事件 → 完成/取消/有限重试 → 容器/Secret回收 → 历史与可追溯结果
```

建图使用一个 `photo_reconstruction` 工作单元；不会把照片当作视频片段独立推理，也没有实现同一地图多机重建。底层复用原 `segments` 表并新增 `kind`，兼容原有 NOT NULL 时间列的 `0/0` 仅为存储兼容值，不表示视频时段、不用于建图进度或耗时估计。对外新增精简 `work_units`，不重复返回大视频帧数组。

### 输入约定

- 上传 ZIP 上限 2 GiB，展开上限 4 GiB、最多3000个成员；选择唯一照片目录、3～500张JPEG、每张≤64 MiB。
- 优先识别唯一 `images/`，兼容已有 Aukerman 的 `park22/`；否则要求唯一JPEG目录。保持照片名，不把随包地图截图当源照片。
- 检查相对路径、重复项、符号链接、加密项、扩展名/JPEG头；顺序读取源照片校验ZIP CRC与SHA256。完整影像解码及可重建性由ODX实际运行确认，上传成功不等于建图必然成功。
- 首版只将所选照片交给引擎。GCP、额外定位、地图、LAZ、DSM等随包文件不进入算法输入。本轮没有下载新数据集。

### 两个建图预设

| 预设 | 核心参数/性质 | 必需文件 |
|---|---|---|
| 标准 | CPU、medium特征、low点云质量、DSM、skip-3dmodel | 正射GeoTIFF、DSM GeoTIFF、LAZ点云、JPEG预览、PDF报告、引擎JSON、相机GeoJSON |
| 快速 | CPU、medium特征、fast-orthophoto、skip-3dmodel | 正射GeoTIFF、JPEG预览、PDF报告、引擎JSON、相机GeoJSON；不要求DSM与稠密点云 |

默认4 CPU、16 GiB内存、32 GiB临时盘、10 cm/px；并行度1～8，分辨率2～100 cm。API允许受限内存/工作盘/时限/重试配置，网页只暴露常用参数。默认任务截止4小时、单次3小时、自动重试0；重新运行创建新任务。无任意额外引擎参数输入。

### K3s与完成语义

- 固定镜像摘要、ARM64架构、选中节点标签与节点名亲和性；普通非root、只读根文件系统、无提权、无ServiceAccount令牌，工作目录与临时目录为有上限的emptyDir。
- 建图不申请 `nvidia.com/gpu`、不使用视频 CUDA 权重；视频镜像及原任务内模型复用保持。
- claim核对真实Job UID、Pod UID、owner、目标/实际节点；attempt令牌与当前工作单元隔离。迟到、取消、旧Pod结果不能发布。
- 阶段来自ODX stdout；不推算伪百分比。先核对引擎完成/版本、照片配准数、空间信息，再上传允许名单文件；服务端校验大小与SHA256并落盘。
- worker的FINALIZING不等于业务成功；只有协调器观察对应Pod成功退出，复查必需文件清单和磁盘内容摘要后才能成功。下载入口只发布当前成功尝试的建图产物；取消或失败留下的部分文件不作为成果展示。
- K3s对象清理与任务终态分开记录；未完成清理之前保留资源占用，不提前重试。

## 4. 本次发现并处理的问题

1. 命名空间旧 `video-budget` 仅12 GiB请求内存，初次16 GiB建图Job被FailedCreate阻止创建Pod。增加三Thor专用覆盖配置 `deploy/thor-workload-quota.yaml`（请求/上限24 CPU、144 GiB、12 Pods），保留旧对象名原位更新。仍有每节点1任务槽与每Job资源限制，并非解除配额。平台补充Job准入错误观测和页面提示。
2. 建图Job/Pod/Secret使用独立应用标签，节点占用盘点同时统计两类标签，避免建图被算成视频或漏掉占用。
3. 处理文件上传与协调器并发更新：结果来源、清单封存、终检摘要和取消状态均核对；同长度文件被篡改的终检反例不能成功。
4. 节点发现不再因视频镜像/权重配置缺失而连带阻止独立建图模板；视频吞吐采样只取具有推理fps的结果，最近一次建图不会清空视频估计值。
5. 首页处理链路与任务列表改为双模板语义；视频预览仍以内联方式提供，不把原预览改成强制下载。

## 6. 当前边界与待办

- **已验证的是单图单节点CPU建图**，不代表GPU建图、多机split-merge、三维网格、DTM、GCP或多光谱已支持。
- 照片包的GPS与10 cm/px栅格参数不等于测绘绝对精度；未做GCP检核、第三方精度验收、同参数多轮性能基准。
- 页面为正射图缩略图、质量摘要和成果下载；没有复刻WebODM地图/三维点云查看器。GeoTIFF、DSM、LAZ可供后续GIS/点云工具使用。
- 当前内存是固定节点预算减平台预留、临时盘是Kubernetes allocatable与Job配额，不冒充实时磁盘余量；运行峰值、磁盘压力以及大于本次77张的数据规模仍需专门测试。
- 运行中物理断电、网络分区、Mac重启与恢复、中间成果断点续算未在本轮实测。自动重试是新attempt从头执行，不是恢复重建检查点。
- **Thor1的K3s Ready不等于资源池可调度**：本轮发现其上报目标为另一地址 `100.100.194.67:8311`，Mac库中最后心跳仍为11月15日，资源池判定OFFLINE。平台按enforce正确排除；两次固定Thor1的排队任务已取消，未绕过资格。没有在本次建图改造中擅自改回该Agent已有上报目的地；本轮重建证据只记Thor2/Thor3。若要三节点都参与当前Mac平台，需对齐Thor1现用资源池上报目标。
- 两种数据集内许可证原文已复制到《数据许可》；ODX基础镜像及依赖来源以先前代码分析及镜像锁定记录为准，正式外发前继续完成第三方授权清单复核。
