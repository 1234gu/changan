# 中期之后的通用任务扩展契约（设计稿，未开放）

## 1. 决策与现状

用户已确认本期只适配视频与建图。本文件是为第三个“通用任务”准备的上层接口和职责约定，**不是可调用的新API、动态插件系统或已通过验收的通用执行能力**。

目前 `GET /api/applications` 返回两条启用情况，创建任务以 `workflow_id` 分派到严格参数模型；运行使用 `metadata.application` 快照、输入标识、工作单元、attempt、K3s Job/Pod身份及成果清单。视频使用 `task_session`，建图使用 `batch_job`。代码仍是两个明确的内置适配器，不宣称已有自动装载任意模型的框架。

## 2. 后续用户应提供什么

1. **镜像引用**：OCI仓库地址与不可变 `sha256`，声明支持架构、协议版本、模型/权重版本；权重与依赖在发布制品内准备，不依赖执行时从公网临时下载。
2. **输入描述**：按角色提供一个或多个平台受管数据集ID、输入格式、数量/大小边界与摘要；不接受主机路径、任意外部URL或通过参数拼接Shell。
3. **参数**：符合应用登记时JSON Schema的结构化JSON；平台拒绝未知字段、越界值与保留字段覆盖。
4. **输出约定**：必需/可选成果角色、文件名或受限相对路径、MIME、格式/空间信息、单件及总大小上限、完成判据。
5. **资源规格**：CPU、内存、临时盘、GPU数量/运行时、单次时限、任务截止时限、重试语义。镜像可运行不等于平台授予其全部资源。

使用者负责算法正确性、数据质量、模型资产和成果语义；平台负责受控准入、部署、调度、过程/失败可追踪、成果完整性与交付。平台不能只因容器退出0就保证模型输出有业务意义。

## 3. 应用登记草案

未来由管理员审核后登记如下对象，普通执行请求只选择登记ID：

```json
{
  "application_id": "user-batch-example",
  "version": "1.0.0",
  "protocol_version": 1,
  "execution_mode": "batch_job",
  "image": "approved-registry/example@sha256:<64hex>",
  "architectures": ["arm64"],
  "input_schema": {"roles": ["dataset"], "allowed_formats": ["zip"]},
  "parameter_schema": {"type": "object", "additionalProperties": false},
  "resource_policy": {"cpu_max": 8, "memory_mib_max": 49152, "gpu_max": 0},
  "output_schema": {"required_roles": ["result"], "max_total_bytes": 4294967296},
  "retry_policy": {"max_attempts": 1, "resume_supported": false}
}
```

这是设计示意，不是当前接口接受的JSON。registry allowlist、镜像扫描/签名、资源审批与协议兼容性检查应在第三类型上线前明确落地；不能仅新增一个“镜像地址”文本框就对外开放。

未来创建通用任务建议仍使用 `POST /api/tasks`，新增受约束的 `application_id + inputs + parameters + resources` 模型；保留两个已有模板的兼容入口。不得把当前内部attempt token、Pod UID、实际节点和产物SHA暴露为用户可指定字段。

## 4. 容器执行契约草案

- 每个工作单元启动一个受限 `batch_job`，批任务工作目录隔离；视频的长会话复用是另一种执行适配器，不强迫所有任务使用视频切片模型。
- `/run/task/payload.json` 只读Secret传入本attempt短生命周期凭证、服务端分配的身份、受管输入下载地址、参数和资源上限；日志必须隐藏凭证。
- 容器先claim实际Pod身份，再流式下载并核对输入摘要。仅在 `/work`、`/tmp` 可写，镜像入口和参数解析不可执行任意用户Shell。
- 事件包含 `task_id, work_unit_id, attempt_id, seq, phase, state`。phase为真实业务阶段，seq单调；未知进度允许不填。服务端校验身份、幂等、状态顺序和终态隔离。
- 输出逐件上传到attempt隔离位置。最终manifest包含输入摘要、镜像/应用版本、实际执行节点/Pod、成果文件角色/相对名/字节数/SHA256、可选业务质量摘要。
- 只有“必需成果持久化和语义检查 + 对应Pod成功退出 + 当前attempt仍有效”共同成立才可成功。取消/超时/旧attempt的晚到产物不得发布。
- 取消依靠K3s终止及资源删除证据；不把HTTP取消响应等同进程已经消失。重试默认新目录从头运行；若未来支持resume，应独立定义可验证checkpoint，而不是复用任意残留目录。

## 5. 展示与下载

通用任务详情提供公共执行信息、事件/错误、资源/镜像身份、文件清单与下载；可按已审核的产物类型扩展图片/文本/表格预览。不得把使用者产生的任意HTML、JavaScript或未净化SVG直接作为同源页面执行。

视频检测与建图地图继续保留专用结果组件。通用任务不能让平台必须理解所有模型业务语义；用户可选择只返回文件，但仍须满足清单完整性和大小限制。

## 6. 建议实施顺序与验收门槛

1. 把现有两分支整理成受控应用注册表：应用描述、schema、输入适配器、资源约束、执行适配器、产物校验器、详情组件。
2. 冻结通用批任务协议/镜像SDK；提供最小文件转换示例镜像及离线测试工具，先在测试命名空间验证。
3. 完成用户/租户隔离、配额、权限、网络出口、镜像准入、数据/产物保留与垃圾回收。当前平台内部演示的安全边界不能自动等同对外多租户产品。
4. 加入“通用任务”选项，先支持单节点CPU批任务，再评估GPU、跨节点DAG和断点能力。
5. 验收必须覆盖：陌生镜像/架构不匹配被拒、缺输入/缺成果/坏摘要不能成功、取消/迟到结果隔离、下载可复核、老视频与建图流程无回归。

本期只完成接口设计留白及可复用的批执行基础；上述后续工作尚未实现或验收，不计入本次成果。
